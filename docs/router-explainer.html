Router: how it picks models and effort

A Claude Code plugin that sorts each prompt into simple, medium or complex, then chooses which Claude model does the work, how hard it thinks, and whether anything checks the result. The goal is to spend less of your subscription without losing much accuracy.

1. What the router does

For every prompt you send, the router decides a tier (how big the job is) and a band (how demanding it is inside that tier). Those two choices fill in a plan: a model for each role, an effort level for each role, and whether a validator runs at the end.

Tiers and roles (TIERS in logic.ts)

TierMain (orchestrator)ExecutorValidatorEscalate
simplehaikusonnet (unused: no orchestration rules are added)nonenone
mediumsonnethaikuopus (only with #validate)opus
complexopussonnetfable (always, unless #novalidate)opus
  • Main: the model that talks to you. A turn.step hook sets its model and effort on every request.
  • Executor: subagents that do the bulk work (search, edit, run commands). The orchestrator is told to delegate to them.
  • Validator: one final subagent whose prompt starts with [verify]; it checks the result and ends with VERDICT: PASS or VERDICT: FAIL.
  • Escalate: the model executors switch to after a failed first attempt (see section 4). null means no cascade.

Effort matrix (EFFORT)

Tier and band pick an effort level for each role. Levels come from Anthropic's effort guidance; max is never used. Highlighted cells are the only ones route() can produce on its own. The others can still occur through the keyword fallback or a #tag override, which keep the band from elsewhere.

Tags you can type in a prompt

Tags are removed from the text before the model sees it. A tag must start the prompt or follow whitespace.

TagEffect
#simple #medium #complexForce the tier for this prompt. The band still comes from the classifier.
#validateTurn the validator on. Sticky across later prompts. Has no effect on simple, which has no validator.
#novalidateTurn the validator off. Sticky.
#autovalidateClear the sticky override; back to the default (complex only).

2. Request flow

Everything starts in the prompt.submit hook and ends in the hooks that shape each model request. The state it sets (tier, band, validation, escalation) is held in the plugin and read by the later hooks.

1Prompt submitted

Slash commands are skipped. Otherwise the plugin starts working on the text. (At session start a separate hook starts the local Laya server if it isn't answering.)

↓
2Parse tags parseTags()

Pulls out #simple/#medium/#complex (tier override) and #validate/#novalidate/#autovalidate (sticky validation override). Cleaned text continues.

↓
3One Laya call, three questions classify()

First 2000 characters, sent to the local Laya server (127.0.0.1:8765, checkpoint typed-decisions). Returns effort, question, repro. 3 s timeout. If Laya is down, a keyword heuristic picks tier and band instead.

↓
4Route route()

Applies the cut-offs to give tier + band. A tag overrides the tier. Validation is needed when the tier is complex. The escalation flag resets, and the status line shows the plan.

↓
5Plan plan()

TIERS[tier] for models, EFFORT[tier][band] for effort, and the validator only if #validate/#novalidate says so, else if the tier needs it.

↓ the plan is read by these hooks while the turn runs
prompt.compose

Adds a system-prompt section (not for simple): act as orchestrator, delegate to the executor model, re-delegate once to the escalate model on STATUS: FAILED, and run a [verify] agent at the end if a validator is set.

turn.step

Main loop: model = main, effort = main effort. Subagent request: effort = validator effort if its model name matches the validator, otherwise executor effort.

agent.spawn

Picks the subagent's model: [verify] prompts get the validator; after an escalation executors are forced to the escalate model; otherwise the call's own model or the executor default. Appends the STATUS or VERDICT rule (not for simple).

tool.call

Watches test commands and Agent results for the free failure signals. On a failure it sets the escalation flag and adds a note to the result the orchestrator reads.

One detail worth knowing: when the validator and the escalate model are the same (medium uses opus for both), the router can't tell them apart by model name alone. That's why verifier prompts are tagged [verify]. For effort, an escalated medium executor gets the validator's effort, which is harmless today because both are medium for the only medium cell route() produces.

3. The classifier

Laya is a small local model that reads the prompt once and answers several questions about it, each independently. The router asks three, in one call (asking them one at a time gave byte-identical numbers, and one call is cheaper). It takes about 0.1 s for short prompts and about 0.65 s at the 2000-character cap.

effort

score, 0–4
"How much engineering effort does this coding request need?"

0 answer or one command · 1 tiny edit · 2 feature or bug fix in a few files · 3 multi-file change with design decisions · 4 large refactor, migration, architecture, deep debugging

question

yes/no probability
"The user is only asking a question and wants no code changed."

repro

yes/no probability
"The request includes an error message, traceback or steps to reproduce."

The rule and its cut-offs (CUTS)

CUTS = { question: 0.8, simple: 1.8, complex: 2.5, repro: 0.3, highBand: 3.0 }

question >= 0.8                        -> simple / low
effort   <  1.8                        -> simple / mid
effort   >= 2.5  and  repro < 0.3      -> complex  (band high if effort >= 3.0, else mid)
otherwise                              -> medium / mid

A prompt with a repro or traceback is a bug report, and bug reports are never routed to complex. Within medium the band is always mid, because nothing in the prompt predicted which bug fixes need a bigger model (see evidence).

Why the old questions were replaced

The first version asked Laya for a tier (pick one of simple/medium/complex), a band and a validation yes/no. The eval (section 5) showed that was weak:

Old questionWhat went wrong
tier (argmax)Over-escalated. On real GitHub issues it sent 342 of 500 ordinary bug fixes to complex (Opus plus a Fable validator).
bandClose to random: ls -la came back high, a JWT migration low.
validationNever said yes (its highest score was 0.49), so in practice only complex was validated.
keyword fallback"Longer than 1200 characters means complex" was wrong. Long prompts were detailed bug reports, not hard tasks. The rule was removed.

Before and after

Held-out balanced accuracy on a 30% split of the 570 labelled prompts (cut-offs fitted on the other 70%). The new figure is 0.77 ± 0.04. The typed-decisions checkpoint beat Laya's default checkpoint on the same held-out data (0.77 vs 0.69). Yes/no risk questions (security, data loss, concurrency) were also tried and dropped: they did not separate risky work on real issues.

4. The cascade

For medium and complex prompts the router starts with a cheaper executor and moves up to Opus only after a failure. It watches for failure without paying for an extra model call.

The reporting lines

  • Every executor prompt gets a rule appended: end with exactly one line, STATUS: DONE (only if a relevant test or concrete check ran and passed) or STATUS: FAILED: <what is wrong or unverified>.
  • Verifier prompts start with [verify] and end with VERDICT: PASS or VERDICT: FAIL: <issues>.
  • Only an explicit FAILED or FAIL counts. A search-only agent that never says DONE does not trigger anything.
  • The simple tier gets no rules and no cascade.

The free failure signals

1. Test command fails

A Bash call matching a known test runner (pytest, jest, cargo test, go test, npm test and others) returns an error, from any agent, during the attempt.

2. Executor says FAILED

The Agent result contains STATUS: FAILED.

3. Verifier says FAIL

The [verify] agent's result contains VERDICT: FAIL. Only runs when a validator is on.

What happens on a failure

  1. An escalation flag is set, at most once per prompt. It resets on the next prompt.
  2. Every later executor for this prompt is forced to the tier's escalate model (opus), even if the call named another model.
  3. A note is added to the failed result: delegate the fix once more to an Agent on the escalate model, pass it the failure details, and don't escalate again.
  4. The status line shows (escalated).
The note is only added when the Agent result is plain text or content blocks. For other result shapes the forced model in agent.spawn and the policy text still escalate, but the explicit note is skipped.

Why not a paid Opus reviewer?

On SWE-bench, putting an Opus review pass on every medium task made the cascade cost $462–501, more than just using Opus for everything ($377). A reviewer only saves money if the failure signal is nearly free, so the shipped version uses the signals above and keeps the paid validator for complex tasks and for #validate.

Key findings

  • Laya separates trivial asks from real work well (AUC above 0.9) and design work from bug fixes reasonably (about 0.8).
  • Among real bug fixes, nothing in the prompt predicts which ones Haiku fails (AUC 0.47–0.56, close to a coin flip). Even human difficulty labels route no better than random. So routing within the medium tier prompt by prompt is pointless, and the router doesn't try.
  • Prompt length points the wrong way: long prompts are detailed bug reports, not hard tasks.
  • Sonnet costs about 87% of Opus per task here and solves fewer (71.4% vs 76.8%).
  • Haiku is 66.6% solved at 44% of Opus's cost. Escalating Haiku to Opus only on a detected failure would reach 79% at $339 (vs $377 for Opus) if detection were perfect. How much of that a free signal captures is the open question.

6. Caveats and open questions

  • The catch rate is unmeasured. The whole cost and solve-rate range depends on how many Haiku failures the free signals actually catch. Logging escalations in real use is the plan for pinning it down.
  • The data is from 4.5-generation models. Haiku, Sonnet and Opus 4.5 at API prices. The effort guidance in the matrix is for the 5.5 models, and TIERS uses short names (haiku, sonnet, opus, fable) that resolve to whatever the current models are. No measurement of the newer models is included. The Fable validator was priced as Opus in the cost model.
  • The eval is a single agent. The SWE-bench runs used one bash-only agent, with no orchestrator and executors. The router's orchestrator-plus-executor structure was not measured.
  • One run per task. Results are noisy.
  • The complex tier is thin. Only 20 complex examples, and they were written by hand, not collected.
  • Not yet tested inside Claude Code. The hook flow was tested with a fake host only. Things not yet confirmed live include whether subagent test commands reach the tool.call hook, the shape of Agent results, and whether the Laya auto-start works from the session hook.
  • Laya must be running. If it isn't, the keyword fallback decides, which is cruder. Validation then still applies to complex only.
  • Within-medium difficulty is not routed. By design, every medium prompt gets the same band, since no signal was found.
