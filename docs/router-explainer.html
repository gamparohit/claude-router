Router: how it picks models and effort

A Claude Code plugin that sorts each prompt into simple, medium or complex, then chooses which Claude model does the work, how hard it thinks, and whether anything checks the result. The goal is to make a Claude subscription last longer.

1. What the router does

For every prompt you send, the router decides a tier (how big the job is) and a band (how demanding it is inside that tier). Those two choices fill in a plan: a model for each role, an effort level for each role, and whether a validator runs at the end.

Tiers and roles (TIERS in logic.ts)

TierMainExecutorValidatorEscalate
simplehaikunot used: Haiku answers on its ownnonenone
mediumhaikuhaikuopus (only with #validate)opus
complexopussonnetfable (always, unless #novalidate)opus
  • Main: the model that talks to you. On medium and complex it is told to act as an orchestrator and delegate.
  • Executor: subagents that do the bulk work (search, edit, run commands).
  • Validator: one final subagent whose prompt starts with [verify]. It checks the result and ends with VERDICT: PASS or VERDICT: FAIL.
  • Escalate: the model executors switch to after a failed first attempt (section 5).

Medium is where almost all real work lands. It starts on Haiku and brings in Opus only after a failure is noticed. An earlier version put Sonnet in charge of medium; in the evidence below Sonnet cost 87% of what Opus did per task and solved fewer, which left little to save.

Effort matrix (EFFORT)

Tier and band pick an effort level for each role. max is never used. Highlighted rows are the ones the evaluator's rule can produce. The others can occur through the keyword fallback or a #tier tag.

2. Request flow

Everything starts when you submit a prompt and ends in the hooks that shape each model request.

1Prompt submitted

Slash commands pass through untouched.

↓
2Parse tags parseTags()

Pulls out a tier tag and the validation tags. The cleaned text continues.

↓
3Short follow-up? isFollowUp()

If the session is already on medium or complex and the prompt is six words or fewer (or was injected by Claude Code), the tier is kept and steps 4 to 6 are skipped.

↓
4Ask Haiku classify()

One call with the first 2000 characters, at low effort, through the session's own model access. It returns three scores. If the call fails or the reply does not parse, a keyword check decides instead.

↓
5Route route()

Fixed cut-offs turn the three scores into a tier and a band.

↓
6Sticky rule ratchet()

In a long conversation the tier can go up but not down. A tier tag skips this.

↓
7Plan plan()

Models from TIERS, effort from EFFORT, validator if the tier is complex or #validate is on. The status line shows the plan.

↓ the plan is read by these hooks while the turn runs
prompt.compose

Adds a system-prompt section (not for simple): delegate to the executor model, re-delegate once to the escalate model after STATUS: FAILED, and run a [verify] agent at the end if a validator is set.

turn.step

Main loop: sets the model and effort, and notes how long the conversation is. Subagent: sets effort only (validator effort if its model name matches the validator, otherwise executor effort).

agent.spawn

Picks the subagent's model: [verify] prompts get the validator; after an escalation executors are forced to the escalate model; otherwise the call's own model or the executor default. Appends the STATUS or VERDICT rule.

tool.call

Watches test commands and subagent results for failure signals. On a failure it sets the escalation flag and adds a note to the result.

turn.complete

When the main turn ends, appends one line to the log (section 5).

3. The evaluator

Claude Haiku reads the prompt and answers three questions in one call. There is nothing to install. Each call uses your own Claude usage: up to about $0.001 per prompt.

effort

Five probabilities, turned into a score from 0 to 4.
"How much engineering effort does this coding request need?"

0 answer or one command · 1 tiny edit · 2 feature or bug fix in a few files · 3 multi-file change with design decisions · 4 large refactor, migration, architecture, deep debugging

question

A probability.
"The user is only asking a question and wants no code changed."

repro

A probability.
"The request includes an error message, traceback or steps to reproduce."

The rule and its cut-offs (CUTS)

CUTS = { question: 0.7, simple: 1.3, complex: 2.4, repro: 0.4, highBand: 3.0 }

question >= 0.7                        -> simple / low
effort   <  1.3                        -> simple / mid
effort   >= 2.4  and  repro < 0.4      -> complex  (band high if effort >= 3.0, else mid)
otherwise                              -> medium / mid

A prompt with an error or a repro is a bug report, and bug reports are never routed to complex. Within medium the band is always mid, because nothing in a prompt predicted which bug fixes need a bigger model.

These cut-offs were fitted on a 570-prompt set that was later found to reward prompt length (every medium example in it was a long GitHub issue). Treat them as starting values. No accuracy figure from that set is quoted here.

Try the rule

A copy of route(), ratchet() and the plan, with the same numbers. It does not call Haiku.

How long it takes

Called through the claude command line, the evaluator took about 5 s. About 1.7 s of that was command-line start-up and about 0.75 s was the model call; the rest was the command line's own context and thinking. The plugin calls Haiku directly at low effort, which should land near 1 s. That has not been timed in a live session.

4. The tier is sticky within a session

Changing the main model in the middle of a conversation abandons that conversation's prompt cache, so the whole history is read again at full price on the new model. Going down a tier and coming back up pays that twice. So the router avoids needless switches:

  • Up is allowed, down is not, once the main loop's last request held six messages or more. In a shorter conversation the tier moves freely.
  • A short follow-up keeps the tier. "continue" or "now add tests" says little about difficulty, so the evaluator is not asked at all. That also saves its wait.
  • In a simple session, short follow-ups are still classified, so "now add tests" after a question can move up.
  • The same tier keeps its band, so effort does not flip between prompts.
  • The status line shows (kept). A tier tag always wins, and /clear starts afresh.
The two thresholds (six messages, six words) are hand picks, not fitted. The worked example behind this rule: with 100,000 tokens of history at API prices, a step on Opus with a warm cache costs about $0.02, and coming back to Opus after its cache has gone costs about $0.50. That assumes caches are kept per model, which Anthropic's page does not state outright.

5. The cascade

On medium and complex the router starts with a cheaper executor and moves to Opus only after a failure. It looks for failure without paying for an extra model call.

The reporting lines

  • Every executor prompt gets a rule appended: end with STATUS: DONE (only if a test or another concrete check ran and passed) or STATUS: FAILED: <what is wrong or unverified>.
  • Verifier prompts end with VERDICT: PASS or VERDICT: FAIL: <issues>.
  • Only an explicit FAILED or FAIL counts. A search-only agent that says neither triggers nothing.

The three free signals

status

The subagent's result contains STATUS: FAILED.

test

The last test command run during the attempt (pytest, jest, cargo test, go test, npm test and others) returned an error.

verdict

The [verify] agent's result contains VERDICT: FAIL. A verifier is judged by its verdict only.

What happens on a failure

  1. An escalation flag is set, at most once per prompt.
  2. Every later executor for this prompt is forced to the escalate model (opus).
  3. A note is added to the failed result: delegate the fix once more, pass on the failure details, and do not escalate again.
  4. The status line shows (escalated).
Why not a paid reviewer on every task? In the SWE-bench data, an Opus review pass on every medium task made the cascade cost more than using Opus for everything.

The log

After each routed prompt, one line is appended to ~/.claude-router/log.jsonl: the tier, whether Haiku, the keyword check, a tag or the sticky rule decided, how many subagents and test commands ran, which signal escalated, and what the retry reported. It holds counts only, never prompt text, and stays on your Mac. ROUTER_LOG=0 turns it off.

node eval/catch-rate.mjs summarises it. It exists to measure how often the router notices a failed cheap attempt. A failure with no failing test leaves no trace, so the catch rate it prints is an upper bound.

What does the catch rate change?

The router only retries failures its free signals notice. That share is not measured, so the simulation was run at 40% and at 80%, with 10% false alarms. Drag to see the range between.

Only the two ends were run (71.2% for $256, and 75.7% for $318). The simulation is linear in the catch rate, so the points between are a straight line.

These figures leave out the main loop. The plugin's medium tier runs a Haiku main loop over Haiku subagents, and that orchestration is not in the data. One estimate, which assumes the main loop adds 15 to 50% of a Haiku run and 80% of failures are caught, puts it at $350 to $408, against $377 for Opus. So the real saving on medium work may be small.

Findings that shaped the design

  • Nothing in a bug-fix prompt predicted which fixes Haiku fails (AUC 0.47 to 0.56, close to a coin flip), and human difficulty labels did no better. So medium is not split further, and failures are caught afterwards.
  • Prompt length is not difficulty: long prompts were mostly detailed bug reports.
  • Sonnet cost 87% of Opus per task and solved fewer (71.4% against 76.8%).

  • Haiku's "only a question" score picks out prompts that led to no edits or commands (AUC 0.74).
  • "Simple" still often means work: 65% of the prompts Haiku called simple were followed by edits or commands.
  • 79% of follow-ups of six words or fewer led to edits or commands, and Haiku would have called 68% of them simple. This is the case the sticky rule covers.
  • The prompt did not predict whether the user's next message was a correction or failure report (AUC 0.47), the same result as on SWE-bench.

Tests

27 tests run against Claude Code's plugin test kit (claude plugin test .). In that kit every model call and tool result is a stand-in, so the tests show the hooks handle the inputs they are given, not that Claude Code sends those inputs.

7. Caveats and open questions

  • Not yet run in a live Claude Code session. Unconfirmed: that subagents' test commands reach the hook, the exact form of a subagent result, and that the Haiku call works from inside the plugin.
  • The catch rate is unmeasured. Every savings figure depends on it. The log is there to measure it.
  • The orchestration is not priced. The cost data is one agent working alone.
  • The cut-offs are starting values, fitted on a set that rewarded prompt length.
  • The cost data is from Claude 4.5 models, one run per task. The plugin uses whatever haiku, sonnet, opus and fable resolve to today.
  • API dollars are not subscription usage. Whether subscription limits count cached reads the way API prices do is unknown, and the sticky rule rests on that.
  • The SWE-chat comparison uses a stand-in for difficulty. Tool-call counts depend on the model and the session, not only on the prompt, and it is one sample of 400.
  • If the Haiku call fails, a keyword check decides, which is cruder.
